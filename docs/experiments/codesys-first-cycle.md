# CODESYS first-cycle detection (for `%S13`)

**Question:** what in CODESYS reproduces Machine Expert – Basic's `%S13`,
which is TRUE for the first scan after every change to RUN?

**Answer:** a `PrepareStart` system-event handler that sets a flag, which the
program clears after its first scan. It fired on every start tested,
including a plain stop → start, and the flag was TRUE for exactly one scan
each time.

- **Run:** 2026-10-18, by the project owner
- **Environment:** CODESYS V3.5 SP22 Patch 3, Control Win (SoftPLC)

## Why not something simpler

- **A self-clearing variable** (`bFirst : BOOL := TRUE;`): it is set only
  when variables are initialised (download, reset). After a plain stop →
  start it stays FALSE, whereas `%S13` is TRUE again.
- **Task information** (`CmpIecTask`, `Task_Info2.dwIECCycleCount`): CODESYS's
  documentation does not say whether the count restarts on stop → start.
- **Schneider's `IsFirstMastCycle`:** only in Schneider's Machine Expert.

CODESYS's documentation describes the events
([System Events tab](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_obj_task_config_sys_event.html)):
`PrepareStart` is "called before starting the application", `StartDone`
"after". A handler is a FUNCTION chosen on Task Configuration → System Events.
The documentation does not say they fire on every start; this run checks
that.

## Setup

Global variable list `GVL`:

```text
VAR_GLOBAL
    bFirstRun : BOOL;
    nPrepare, nStartDone, nFirstScans : INT;
END_VAR
```

Task Configuration → System Events:

| Event | Function | Body |
| --- | --- | --- |
| `PrepareStart` | `OnPrepareStart` | `GVL.bFirstRun := TRUE; GVL.nPrepare := GVL.nPrepare + 1;` |
| `StartDone` | `OnStartDone` | `GVL.nStartDone := GVL.nStartDone + 1;` |

`PLC_PRG`, in the cyclic task:

```text
IF GVL.bFirstRun THEN
    GVL.nFirstScans := GVL.nFirstScans + 1;
END_IF;
GVL.bFirstRun := FALSE;
```

## Results

Values read after each action:

| Action | `nPrepare` | `nStartDone` | `nFirstScans` | `bFirstRun` |
| --- | --- | --- | --- | --- |
| Login (download) | 0 | 0 | 0 | FALSE |
| Start | 1 | 1 | 1 | FALSE |
| Stop | 1 | 1 | 1 | FALSE |
| Reset warm | 0 | 0 | 0 | FALSE |
| Start | 1 | 1 | 1 | FALSE |
| Reset cold | 0 | 0 | 0 | FALSE |
| Start | 1 | 1 | 1 | FALSE |

Then, from a fresh start (all counters 1):

| Action | `nPrepare` | `nStartDone` | `nFirstScans` |
| --- | --- | --- | --- |
| Stop → Start | 2 | 2 | 2 |
| Stop → Start | 3 | 3 | 3 |

## Findings

- **`PrepareStart` fires on every start:** after download, after each reset,
  and after a plain stop.
- **It runs before the first cycle:** `nFirstScans` rose with every start, so
  the program saw the flag on its first scan.
- **The flag lasts exactly one scan:** `nFirstScans` rose by one per start,
  never more.
- **Resets re-initialise the counters to 0,** as expected for non-retain
  variables.
- **`StartDone` also fired every time.** It was not tested whether it runs
  before or after the first cycle, so `PrepareStart` is the one to use.

## The PLCopen XML export

CODESYS's Export PLCopenXML dialog lists Device, Application, GVL, Library
Manager, `MainTask`, the two handler functions and `PLC_PRG`. It has **no
Task Configuration entry**, and that object holds the System Events
bindings. The export with everything ticked contains:

- **The handler functions:** ordinary `function` POUs, each returning `DWORD`
  with one `VAR_IN_OUT EventPrm : CmpApp.EVTPARAM_CmpApp`, and the comment
  "Do not change the interface of this function! This function is
  implicitly generated by the 'Task Configuration'…".
- **The task:** `MainTask` with its `tasksettings`, as before.
- **The libraries:** besides the template's, `CmpEventMgr` 3.5.17.0,
  `Component Manager` 3.5.21.0, `CmpApp` 3.5.21.0 and `CmpIecTask` 3.5.21.0,
  all `(System)`, as `#Name` placeholder entries. Not yet known: whether
  adding the event handlers is what added them.

It does **not** contain the binding of `PrepareStart` to `OnPrepareStart`:
no element names either event. **Importing it confirmed the loss:** in a
new project (template Application deleted first), Task Configuration →
System Events was empty. The functions arrive, but nothing calls them until
the event is bound, by hand or by the script below.

## Restoring the binding by script

CODESYS's **native** export (`export_native`, not PLCopen) of the Task
Configuration does hold the binding, as an `alSysEventList` entry:

```xml
<Single Type="{357faaca-a279-4878-8c2f-ec7c49896fa3}" Method="IArchivable">
  <Single Name="Eventname" Type="string">PrepareStart</Single>
  <Single Name="Description" Type="string">Called before application starts. Context=Communication task. Debugging=Disabled</Single>
  <Single Name="stComponentId" Type="string">CmpApp.EventIDs.CMPID_CmpApp</Single>
  <Single Name="stEventId" Type="string">CmpApp.EventIDs.EVT_PrepareStart</Single>
  <Single Name="stParameterId" Type="string">CmpApp.EventIDs.EVTPARAMID_CmpApp</Single>
  <Single Name="stParameterVersion" Type="string">CmpApp.EventIDs.EVTVERSION_CmpApp</Single>
  <Single Name="ParameterStruct" Type="string">CmpApp.EVTPARAM_CmpApp</Single>
  <Null Name="Library" />
  <Single Name="Active" Type="bool">True</Single>
  <Single Name="FunctionToCall" Type="string">OnPrepareStart</Single>
  <Single Name="Position" Type="short">0</Single>
</Single>
```

A CODESYS script run in the imported project restored it:

1. Export the project's own Task Configuration natively (so every ID is
   that project's).
2. Add the entry above. In a project that never had a handler the list is
   `<Null Name="alSysEventList" />`, not an empty `List2`.
3. **Remove** the Task Configuration, then `import_native` the edited file
   into the application. Importing over the existing one is not enough: it
   raised a conflict only for `MainTask` and kept the Task Configuration,
   event list included.
4. Export it again to check.

Run 3 of the script: System Events showed `PrepareStart` → `OnPrepareStart`,
Active. The project built, and online `nPrepare` and `nFirstScans` read 2
after Start → Stop → Start (`nStartDone` 0: that event was not bound). So the
imported handler, with its `CmpApp` parameter, compiles and is called.

The scripting objects list nothing through `dir()`, so the API's own
members were no help; `NativeImportResolve` has `replace`, `skip` and
`cancel`.

## Not yet established

- **Other targets:** the events offered depend on the device; only the
