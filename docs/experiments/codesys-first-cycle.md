# CODESYS first-cycle detection (for `%S13`)

**Question:** what in CODESYS reproduces Machine Expert – Basic's `%S13`,
which is TRUE for the first scan after every change to RUN?

**Answer:** a `PrepareStart` system-event handler that sets a flag, which the
program clears after its first scan. It fired on every start tested,
including a plain stop → start, and the flag was TRUE for exactly one scan
each time.

- **Run:** 2026-10-18, by the project owner
- **Environment:** CODESYS V3.5 SP22 Patch 3, Control Win (SoftPLC)

## Why not something simpler

- **A self-clearing variable** (`bFirst : BOOL := TRUE;`): it is set only
  when variables are initialised (download, reset). After a plain stop →
  start it stays FALSE, whereas `%S13` is TRUE again.
- **Task information** (`CmpIecTask`, `Task_Info2.dwIECCycleCount`): CODESYS's
  documentation does not say whether the count restarts on stop → start.
- **Schneider's `IsFirstMastCycle`:** only in Schneider's Machine Expert.

CODESYS's documentation describes the events
([System Events tab](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_obj_task_config_sys_event.html)):
`PrepareStart` is "called before starting the application", `StartDone`
"after". A handler is a FUNCTION chosen on Task Configuration → System Events.
The documentation does not say they fire on every start; this run checks
that.

## Setup

Global variable list `GVL`:

```text
VAR_GLOBAL
    bFirstRun : BOOL;
    nPrepare, nStartDone, nFirstScans : INT;
END_VAR
```

Task Configuration → System Events:

| Event | Function | Body |
| --- | --- | --- |
| `PrepareStart` | `OnPrepareStart` | `GVL.bFirstRun := TRUE; GVL.nPrepare := GVL.nPrepare + 1;` |
| `StartDone` | `OnStartDone` | `GVL.nStartDone := GVL.nStartDone + 1;` |

`PLC_PRG`, in the cyclic task:

```text
IF GVL.bFirstRun THEN
    GVL.nFirstScans := GVL.nFirstScans + 1;
END_IF;
GVL.bFirstRun := FALSE;
```

## Results

Values read after each action:

| Action | `nPrepare` | `nStartDone` | `nFirstScans` | `bFirstRun` |
| --- | --- | --- | --- | --- |
| Login (download) | 0 | 0 | 0 | FALSE |
| Start | 1 | 1 | 1 | FALSE |
| Stop | 1 | 1 | 1 | FALSE |
| Reset warm | 0 | 0 | 0 | FALSE |
| Start | 1 | 1 | 1 | FALSE |
| Reset cold | 0 | 0 | 0 | FALSE |
| Start | 1 | 1 | 1 | FALSE |

Then, from a fresh start (all counters 1):

| Action | `nPrepare` | `nStartDone` | `nFirstScans` |
| --- | --- | --- | --- |
| Stop → Start | 2 | 2 | 2 |
| Stop → Start | 3 | 3 | 3 |

## Findings

- **`PrepareStart` fires on every start:** after download, after each reset,
  and after a plain stop.
- **It runs before the first cycle:** `nFirstScans` rose with every start, so
  the program saw the flag on its first scan.
- **The flag lasts exactly one scan:** `nFirstScans` rose by one per start,
  never more.
- **Resets re-initialise the counters to 0,** as expected for non-retain
  variables.
- **`StartDone` also fired every time.** It was not tested whether it runs
  before or after the first cycle, so `PrepareStart` is the one to use.

## The PLCopen XML export

CODESYS's Export PLCopenXML dialog lists Device, Application, GVL, Library
Manager, `MainTask`, the two handler functions and `PLC_PRG`. It has **no
Task Configuration entry**, and that object holds the System Events
bindings. The export with everything ticked contains:

- **The handler functions:** ordinary `function` POUs, each returning `DWORD`
  with one `VAR_IN_OUT EventPrm : CmpApp.EVTPARAM_CmpApp`, and the comment
  "Do not change the interface of this function! This function is
  implicitly generated by the 'Task Configuration'…".
- **The task:** `MainTask` with its `tasksettings`, as before.
- **The libraries:** besides the template's, `CmpEventMgr` 3.5.17.0,
  `Component Manager` 3.5.21.0, `CmpApp` 3.5.21.0 and `CmpIecTask` 3.5.21.0,
  all `(System)`, as `#Name` placeholder entries. Not yet known: whether
  adding the event handlers is what added them.

It does **not** contain the binding of `PrepareStart` to `OnPrepareStart`:
no element names either event. **Importing it confirmed the loss:** in a
new project (template Application deleted first), Task Configuration →
System Events was empty. The functions arrive, but nothing calls them until
the event is bound, by hand or by the script below.

## Restoring the binding by script

CODESYS's **native** export (`export_native`, not PLCopen) of the Task
Configuration does hold the binding, as an `alSysEventList` entry:

```xml
<Single Type="{357faaca-a279-4878-8c2f-ec7c49896fa3}" Method="IArchivable">
  <Single Name="Eventname" Type="string">PrepareStart</Single>
  <Single Name="Description" Type="string">Called before application starts. Context=Communication task. Debugging=Disabled</Single>
  <Single Name="stComponentId" Type="string">CmpApp.EventIDs.CMPID_CmpApp</Single>
  <Single Name="stEventId" Type="string">CmpApp.EventIDs.EVT_PrepareStart</Single>
  <Single Name="stParameterId" Type="string">CmpApp.EventIDs.EVTPARAMID_CmpApp</Single>
  <Single Name="stParameterVersion" Type="string">CmpApp.EventIDs.EVTVERSION_CmpApp</Single>
  <Single Name="ParameterStruct" Type="string">CmpApp.EVTPARAM_CmpApp</Single>
  <Null Name="Library" />
  <Single Name="Active" Type="bool">True</Single>
  <Single Name="FunctionToCall" Type="string">OnPrepareStart</Single>
  <Single Name="Position" Type="short">0</Single>
</Single>
```

A CODESYS script run in the imported project restored it:

1. Export the project's own Task Configuration natively (so every ID is
   that project's).
2. Add the entry above. In a project that never had a handler the list is
   `<Null Name="alSysEventList" />`, not an empty `List2`.
3. **Remove** the Task Configuration, then `import_native` the edited file
   into the application. Importing over the existing one is not enough: it
   raised a conflict only for `MainTask` and kept the Task Configuration,
   event list included.
4. Export it again to check.

Run 3 of the script: System Events showed `PrepareStart` → `OnPrepareStart`,
Active. The project built, and online `nPrepare` and `nFirstScans` read 2
after Start → Stop → Start (`nStartDone` 0: that event was not bound). So the
imported handler, with its `CmpApp` parameter, compiles and is called.

The scripting objects list nothing through `dir()`, so the API's own
members were no help; `NativeImportResolve` has `replace`, `skip` and
`cancel`.

## The converted sample

TwinForge's CODESYS export now writes, when the logic uses `%S13`:
`TF_OnPrepareStart` (the handler's interface as CODESYS generates it, body
`ControllerTags.SB_FIRSTRUN := TRUE;`), `TF_EndOfScan` (clears it, called
last in `MAST`), the four libraries above, and a
`system_event_binding_required` diagnostic. The script, as
[`bind_system_events.py`](../../examples/CODESYS/scripts/bind_system_events.py),
binds each `TF_On<Event>` handler it finds.

Run on 2026-10-18 with `ld_laba2.smbp` (a downloaded sample whose rung 0 is
`%S13` → set `S_IDLE`, reset the other step bits):

1. Imported into a new project (template Application deleted), ran the
   script, built: no errors.
2. Login → Start: `S_IDLE` TRUE, the other step bits FALSE.
3. Wrote `S_IDLE` := FALSE, `S_LOAD1` := TRUE; Stop → Start: `S_IDLE` TRUE
   and `S_LOAD1` FALSE again.

So the converted program sees `%S13` on the first scan after a plain
stop → start, as on the M221.

## Cold and warm start (`%S0`, `%S1`)

**Question:** which CODESYS starts are Machine Expert – Basic's cold and
warm starts? The M221 Programming Guide (EIO0000003297.04, "Controller
State Transitions") defines:

- **Cold start:** "all data initialized to its default values". It happens
  on download, Initialize controller, power-up without a charged battery,
  and booting without a validated application. `%S0` is TRUE "during the
  first complete scan" ("System Bits (%S)").
- **Warm start:** a power return with data backup; the program "resumes
  running the program, in its previous operating state, with the
  counters, function blocks, and system words and bits maintained". `%S1`
  is TRUE until the end of that scan.

**Method:** two flags, each TRUE only until the first scan clears it. A
RETAIN flag is re-initialised only when RETAIN data is (cold); a non-retain
one also when only non-retain data is (warm). The PrepareStart handler above
marks the first scan. Also an `FB_init` probe, which records its
`bInitRetains` and `bInCopyCode` parameters
([CODESYS: FB_init](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_method_fb_init_fb_reinit.html)).

Added to the same project:

```text
VAR_GLOBAL
    bNonRetainInit : BOOL := TRUE;
    bStartWasCold, bStartWasWarm : BOOL;
    nStarts : INT;
END_VAR
VAR_GLOBAL RETAIN
    bRetainInit : BOOL := TRUE;
END_VAR
```

`PLC_PRG` (with `Probe : FB_StartProbe;` declared):

```text
IF GVL.bFirstRun THEN
    GVL.bStartWasCold := GVL.bRetainInit;
    GVL.bStartWasWarm := GVL.bNonRetainInit AND NOT GVL.bRetainInit;
    GVL.nStarts := GVL.nStarts + 1;
END_IF;
GVL.bRetainInit := FALSE;
GVL.bNonRetainInit := FALSE;
GVL.bFirstRun := FALSE;
```

`FB_StartProbe.FB_init`: `xInitRetains := bInitRetains; xInCopyCode :=
bInCopyCode; nInits := nInits + 1;`

**Results** (2026-10-18, Control Win), read after each action:

| Action | cold | warm | `nStarts` | `xInitRetains` | `xInCopyCode` |
| --- | --- | --- | --- | --- | --- |
| Login (download) | FALSE | FALSE | 0 | TRUE | FALSE |
| Start | **TRUE** | FALSE | 1 | TRUE | FALSE |
| Stop → Start | FALSE | FALSE | 2 | TRUE | FALSE |
| Reset warm | FALSE | FALSE | 0 | FALSE | FALSE |
| Start | FALSE | **TRUE** | 1 | FALSE | FALSE |
| Reset cold | FALSE | FALSE | 0 | TRUE | FALSE |
| Start | **TRUE** | FALSE | 1 | TRUE | FALSE |
| Runtime restart (tray: Stop PLC, Start PLC; login without download) | FALSE | **TRUE** | 1 | FALSE | FALSE |
| Online change (comment in `PLC_PRG`) | FALSE | TRUE | 1 | FALSE | FALSE |
| Online change (variable added to `FB_StartProbe`) | FALSE | TRUE | 1 | FALSE | FALSE |

`nInits` read 1 throughout: the instance is initialised before `FB_init`
runs, so it cannot count calls.

**Findings:**

- **Cold (`%S0`):** download and Reset cold: RETAIN data initialised.
- **Warm (`%S1`):** Reset warm and a runtime restart: non-retain data
  initialised, RETAIN data kept. Control Win kept the RETAIN flag across the
  restart, the nearest equivalent of the M221's power return with backup.
- **Neither:** a plain stop → start (only `%S13`, `nStarts` 1 → 2).
- **`FB_init` agrees with the flags:** `bInitRetains` TRUE at download and
  Reset cold, FALSE at Reset warm and the restart. This settles CODESYS's
  ambiguous note "(reset warm / reset cold)": a warm reset gives FALSE.
- **Online change fires nothing:** `nStarts` and the flags stayed as they
  were, so `PrepareStart` does not fire on an online change, as `%S13`
  requires. After the declaration change `xInCopyCode` still read FALSE:
  per CODESYS's documented order the old instance's values are copied over
  the new one after `FB_init`, so the probe cannot show that call.

**The converted test** (2026-10-18): fixture 14 with three rungs added,
`%S13` → reset `%M20`, `%M21`; `%S0` → set `%M20`; `%S1` → set `%M21`.
TwinForge's export adds `TF_StartFlags` (`TF_NonRetainInit`, and
`TF_RetainInit` as RETAIN, in the mixed-list form of CODESYS's export of
`GVL`), and `TF_OnPrepareStart` sets `%S0` from `TF_RetainInit` and `%S1`
from `TF_NonRetainInit AND NOT TF_RetainInit` before clearing both. After
the import and the binding script, the list showed `TF_RetainInit` under
`VAR_GLOBAL RETAIN`, and every row came out as expected:

| Action | `%M20` (cold) | `%M21` (warm) |
| --- | --- | --- |
| Download → Start | TRUE | FALSE |
| Stop → Start | FALSE | FALSE |
| Reset warm → Start | FALSE | TRUE |
| Reset cold → Start | TRUE | FALSE |
| Runtime restart | FALSE | TRUE |

So the handler runs after the start's initialisation, and the flags read
there tell the starts apart as they did in the first scan.

An export of a list declared only `VAR_GLOBAL RETAIN` came out with no
RETAIN marking at all; most likely the keyword was missing from that
declaration, so this is not recorded as a CODESYS rule.

**A difference this exposes:** the M221 keeps all its data on a warm start;
CODESYS keeps only RETAIN (and PERSISTENT) variables. TwinForge declares
converted `%M`/`%MW` as ordinary variables, so a runtime restart clears them
where the M221 would not.
